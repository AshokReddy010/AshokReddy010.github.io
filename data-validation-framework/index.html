Data Validation Framework

I planted six errors in invented data, and the checks found all six with the right reason, with no false alarms on 113 clean days. A live console rebuilds 60 days of three simulated systems every morning, injects random faults the checks are not told about, and scores whether every one was caught with the right reason.

Reconciliation Console

Three systems should hold the same transactions: a transaction system, a client file feed and a billing database. Every morning a simulator rebuilds the last 60 days of all three and quietly breaks a few of them: drops records, bills some twice, changes or blanks amounts, files records a day late. The dbt checks are never told what was broken. This page shows whether they found it.

How the checks work

Level 1: totals

Count rows and sum amounts per source per day, and compare each feed with the transaction system. Most days end here with one cheap comparison.

Level 2: records

Only for days that break: join record by record and name the reason (missing, duplicate, wrong date, blank amount or different amount).

Guard tests

dbt tests fail the run if a break has no record-level reason, or if a matching day still hides exceptions (two errors cancelling out in the totals).

All data is simulated; no real or employer data is used. Code, dbt models and tests on GitHub.

Case notes

When the same transactions live in several systems, a late file, a double-billed record or a blank amount can reach a client report unnoticed. Checking by hand before every delivery is slow and misses small differences.

Approach

  • Level 1: count the rows and total the amounts per source per day, then compare each source with the transaction system.
  • Level 2: for the days that differ, find the records behind the difference and name the reason: missing, duplicate, wrong date, blank amount or different amount.
  • Output: one results table per source per day, a written report, a chart and an optional chat alert.
  • Proof: the data generator plants six known errors, so the checks can be scored against them.

What it found

  • All six: 37 missing records, 25 duplicates, 12 changed amounts, one missing day, 9 records filed under the wrong day and 5 blank amounts.
  • Totals matter: on two of the days every record was present, so a row count alone would have passed them.
  • No noise: none of the 113 clean source-days was flagged.

What made it hard

  • Two days, one cause: a record filed under the wrong day throws off the day it left and the day it landed on. My first drill-down explained only one, and a test I had written for the checks themselves caught it.
  • Testing the tester: three dbt tests guard the checks, including one that fails if a clean-looking day hides errors that cancel out.
  • Limits: the data is invented and small, the transaction system is assumed correct, and matching relies on a shared transaction ID.

Repository

Three systems hold the same transactions: the transaction system, a client file feed and the billing database. Before any report goes out, they should agree. This project checks that they do, every day, and says exactly which records are wrong when they do not.

It is a public example of the kind of reconciliation checks I build at work. All data here is invented, and no employer code, data or business rule is used.

▶ Live reconciliation console: every morning a scheduled job rebuilds the last 60 days of all three systems, injects random faults the checks are not told about (dropped and duplicated records, changed and blank amounts, a missing day, records filed a day late), runs the dbt checks, and scores them: every fault caught with the right reason, and no false alarms. Faults are seeded by date, so a day's faults are reproducible (python scripts/live.py --end 2026-10-17). unit_tests/test_live.py holds the checks to a perfect score on two windows.

How it works

The checks run in two levels, so most days cost one cheap comparison.

Level Model What it does
1 daily_totals Counts the rows and sums the amounts per source per day
1 recon_daily Compares each source with the transaction system and marks each day match or break
2 recon_exceptions For records that disagree, names the reason: missing, duplicate, wrong date, blank amount or different amount
Output check_results One row per source per day with the status, the differences and the reasons, for a dashboard or an alert to read 
scripts/generate_data.py     three invented sources, six planted errors
        │
dbt (DuckDB)
  ├─ staging                 cast types, treat blank amounts as null
  ├─ daily_totals            level 1: counts and totals
  ├─ recon_daily             level 1: match or break, per source per day
  ├─ recon_exceptions        level 2: the records behind each break
  └─ check_results           the table people read
        │
scripts/run_checks.py        report, chart and alert

Tests

  • 21 dbt data tests. Keys are unique and present, every feed and billing record points to a real transaction, and three tests guard the checks themselves:
  • every break has a record-level reason,
  • no clean day hides exception records, which would mean two errors cancelled out in the totals,
  • a warning is raised while any break is open.
  • 10 pytest checks that the breaks found are exactly the planted ones, with the right reason and record count for each.

The second of those tests caught a real gap while I was building this. A record filed under the wrong day throws off two days, the one it left and the one it landed on. My first drill-down explained only the first, and the test failed until it explained both.

Scheduling and alerts

  • scheduled-validation.yml runs the checks every day on GitHub Actions and can be started by hand.
  • The report is written to the run summary and saved as a file with the run.
  • If an ALERT_WEBHOOK_URL secret is set, a break posts a message to that chat webhook.

Run it yourself

Needs Python 3.10 or newer. Commands are for Windows CMD.

git clone https://github.com/AshokReddy010/data-validation-framework.git
cd data-validation-framework
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt

python scripts\run_checks.py
pytest -q unit_tests

run_checks.py creates the data, builds the checks and writes reports/summary.md, reports/check_results.csv, reports/exceptions.csv and the chart. Add --fail-on-break to make it exit with an error while any break is open.

Limitations

  • The data is invented and small: 12,000 transactions over 60 days. It shows the method, not performance at scale.
  • The transaction system is treated as correct. A record wrong in that system and repeated faithfully by the others would not be caught.
  • Matching is by transaction ID. Sources without a shared key would need a matching step first.
  • It runs on DuckDB. The models use standard SQL and dbt, so moving them to a cloud warehouse is a change of profile, which is the planned next step.
  • A scheduler such as Airflow would replace the GitHub Actions schedule in a production set-up.
